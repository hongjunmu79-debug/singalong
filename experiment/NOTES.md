# 实验记录

## 要回答的问题

8 秒现场片段 + 几十首的闭集曲库，top-1 命中率够不够支撑「自动识别 → 我确认」这套设计。

## 已固定的参数

| 项 | 取值 | 说明 |
|---|---|---|
| 采样率 | 11025 Hz | 够覆盖 200–4000 Hz 的音乐能量 |
| n_fft / hop | 1024 / 512 | hop 从 256 提到 512 后抗噪和抗混响都明显变好 |
| 峰值 | 逐帧中位数 + 10 dB，7×7 邻域局部极大 | 比全局百分位阈值稳 |
| 配对 | 每峰连后 5 峰，dt ≤ 63 帧 | 约 2.9 秒 |
| 检索 | dt 容差 ±1 帧，(歌曲, 偏移) 投票取最大 | ±2 无进一步收益 |
| 实测 | 峰值 ~10/s，单次查询中位 25 ms | Python 实现，WASM 只会更快 |

## 合成数据基线

用 6 首合成曲（正弦和弦 + 打击乐，各 70 秒），每首取 6 段 8 秒片段。

| 条件 | top-1 |
|---|---|
| 干净 | 100% |
| 噪声 10 dB | 100% |
| 噪声 5 dB | 94.4% |
| 噪声 0 dB | 88.9% |
| 噪声 -5 dB | 75.0% |
| 混响 RT60 1.5s | 77.8% |
| 混响 RT60 2.5s | 69.4% |
| 混响 1.5s + 噪声 0 dB | 55.6% |
| 混响 2.5s + 噪声 -5 dB | 33.3% |
| AGC + 降噪 + 噪声 0 dB | 77.8% |

每组 36 个样本，一个样本就是 2.8 个百分点，差异小的行不要当真。

## 已经确认的

1. **管线是对的** —— 干净条件下 100%，说明建库、哈希、投票这条链条没写错。
2. **hop 512 优于 256** —— 这个提升在噪声和混响两类条件下都出现，不是单点波动。
3. **dt 容差 ±1 有效** —— 混响会把峰值时间抹开几十毫秒，精确配对会整片失效。
4. **性能不是瓶颈** —— 单次查询 25 ms，手机 WASM 只会更快。
5. **严重退化时绝对得分会塌** —— 混响叠加噪声后，匹配率掉到 1% 以下，靠绝对分数做全自动判定不可行。这反过来支持了「提示疑似 → 用户确认」的设计，而不是全自动切歌。

## 途中修掉的一个建模错误

第一版混响把干声完全卷进了脉冲响应，等于把直达声整个消掉，是「只有混响、没有直达声」的极端情况，现实中不存在。改成干声与混响按比例混合（默认各占一半）后，混响 1.5s 从 58% 回到 78%。

**这件事的教训**：实验里的「现场」建模如果偏了，得到的就是假结论。真实数据比任何合成条件都重要。

## 合成数据回答不了的

- **真实音乐**的表现。合成曲是稳定的正弦和弦，对宽带噪声和混响异常脆弱；真实音乐有歌词、打击乐、更宽的动态范围，结构丰富得多。
- **现场版对录音室版**。编曲、调性、速度都会变，这是产品真正的难点，也是这个实验唯一重要的那一段。

所以上面那张表只能说明「管线没问题、参数在合理区间」，**不能当成产品可行性结论**。

## 怎么跑真实数据


- 歌放 `drop/studio/`，文件名即歌名
- 现场录音放 `drop/live/`，文件名里带歌名
- 报告写到 `out/report.md`

## 拿到真实数据后的判断标准

| 现场 top-1 | 结论 |
|---|---|
| ≥ 90% | 按原方案实现，自动识别 + 确认提示够用 |
| 70–90% | 加长采样到 10–12 秒，或多段投票 |
| < 70% | 换旋律特征（chroma + 对齐），或上原生壳拿干净音频 |

## 现场录音自匹配（2026-11-05）

只有一个 33.9 秒的现场视频，没有录音室版，所以做了一个**不需要参照**的测试：
索引和查询都来自同一段录音，看加噪/加混响后票数峰值是否仍落在真实时间偏移上。

| 条件 | 偏移命中 | 中位匹配率 |
|---|---|---|
| 干净 | 100% | 24.4% |
| 噪声 10dB | 100% | 15.1% |
| 噪声 5dB | 100% | 10.6% |
| 噪声 0dB | 100% | 6.8% |
| 噪声 -5dB | 100% | 4.8% |
| 混响 1.5s | 100% | 4.9% |
| 混响 2.5s | 100% | 4.8% |
| 混响 1.5s + 噪声 0dB | 75% | 1.5% |

**结论**

- 真实录音的指纹稳定性显著好于合成曲 —— 同条件下匹配率是合成数据的 3–5 倍。这说明前面那张合成表**低估**了真实音频。
- 这段录音虽然有削波和高频缺失，仍扛得住 0dB 噪声和 2.5s 混响。
- 只有「混响 + 噪声」叠加时开始掉，4 个窗口掉 1 个。

**局限（比结论更重要）**

- 只有 4 个窗口，一个样本就是 25 个百分点，不能当准确率看
- 自匹配比「现场对录音室」容易得多，数字必然偏乐观
- 这段录音高频基本没了，不代表正常录音
- 这个测试只能证伪，不能证成

## 真实音乐基线（2026-11-06）

曲库：30 首真实 MP3（本机音乐库，不同歌手），总时长约 2 小时。
索引 1,422,432 条哈希，峰值密度 58.8/s，建索引 33 秒。
每首 6 段 8 秒，每个条件 180 次查询。

| 条件 | 真实音乐 | 合成数据 | 差值 |
|---|---|---|---|
| 干净 | 99.4% | 100% | −0.6 |
| 噪声 10dB | 99.4% | 100% | −0.6 |
| 噪声 5dB | 98.3% | 94.4% | **+3.9** |
| 噪声 0dB | 97.2% | 88.9% | **+8.3** |
| 噪声 −5dB | 93.3% | 75.0% | **+18.3** |
| 混响 1.5s | 99.4% | 77.8% | **+21.6** |
| 混响 2.5s | 100.0% | 69.4% | **+30.6** |
| 混响 1.5s + 噪声 0dB | 81.1% | 55.6% | **+25.5** |
| 混响 2.5s + 噪声 −5dB | 61.7% | 33.3% | **+28.4** |
| AGC + 降噪 + 噪声 0dB | 96.1% | 77.8% | **+18.3** |

单次查询中位 40ms，p95 90ms。

**结论**

1. **合成数据系统性低估了能力**，尤其在混响上差 20–30 个百分点。之前那张表只能用来验证管线，不能用来判断可行性。
2. 最差条件（2.5s 混响 + −5dB 噪声）仍有 61.7%，配合「提示 + 确认」是可用的。
3. 真实音乐的频谱结构远比正弦和弦丰富，这正是地标指纹需要的东西。

**仍然存在的偏差（重要）**

- 这 30 首是**不同歌手**，而真实演出的曲库是同一歌手 20–30 首，嗓音、编曲、混音更接近，匹配会更难。本次数字**偏乐观**。
- 仍然是**自查询**（同一段录音对自己），比「现场对录音室」容易得多。
- 所以这张表是**上限**，不是现场表现。

**确认阈值（按混响 1.5s + 噪声 0dB 条件统计）**

| 阈值 | 正确结果覆盖率 | 误报率 |
|---|---|---|
| 0.5% | 100.0% | 100.0% |
| 1.0% | 89.7% | 17.6% |
| 2.0% | 40.4% | 8.8% |
| 3.0% | 19.9% | 2.9% |
| 5.0% | 2.1% | 0.0% |

原来拍的 2% 只覆盖 40% 的正确结果，会让大部分识别退化成「没听清」。已改成 **1%**（覆盖 89.7%，误报 17.6%）—— 在「用户一秒钟确认」的设计下，误报的代价是一句话，漏报的代价是用户手动选歌。

## 还缺什么

真正的结论仍然只能来自「现场录音 → 录音室版」的闭集查询。目前只有一段 34 秒的现场视频，且不知道是哪首歌，没有对应录音室版，无法比对。

在此之前，确认阈值按上表取 1%，但**仍然算临时值**。
